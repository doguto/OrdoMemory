# Runtimeテーブル データ構造の比較結果

`RuntimeTable.Proposal.md` の候補と、その他の既知の構造を同じ条件で実装・計測し、採用する構造を決める.
コードと再現手順は `bench/RuntimeTableBench/`. 生の結果 (全指標) は `bench/RuntimeTableBench/results/`.

## 条件

- N = 1,000,000 件. 3 回計測した中央値.
- Record は 32B の struct (`int Id, Score, Category; string Name, Description`). 文字列本体は共有しており、メモリに含まない.
- ランタイム: CoreCLR (.NET 8.0) / Mono 6.8 (SGen GC, Unity の Mono バックエンドの近似). Intel Xeon 2.1GHz.
- popcount は netstandard2.1 に合わせ SWAR. データ構造のコードが netstandard2.1 / C# 9 でコンパイルできることを `bench/NetStandardCheck` で確認済み.
- 計測前に、全実装を参照実装 (`SortedDictionary` / `SortedSet`) と乱数操作で突き合わせて検証している (`verify`).

### 読み取れること

1. **現行案 (A) は全項目で最下位級**. 削除が累積すると Find が 7 倍遅くなり (73 → 528ns)、全体コンパクションで 14〜24ms 止まる. 1 行あたり約 62B.
2. **設計案の初版 (C) も採用できない**. 最大遅延は小さいが、乱順の削除が B の 2.7 倍遅く、全件列挙も遅い. Mono では乱順削除の後のメモリが 106B/行まで膨らむ. ブロックごとに小さな配列を持つことで、配列ヘッダの読み込みと確保が増えるのが原因.
3. **B (rank テーブル) は処理量が最良**だが、全体コンパクションで 16〜21ms のスパイクが残る. 60fps (16.7ms / フレーム) を 1 回で超える.
4. **G (区画分け rank テーブル) は、B とほぼ同じ速さのままスパイクを区画単位 (約 25µs) に抑え、メモリも最小**. Key 順を保つ構造の中では総合で最良.
5. **D (ECS 方式) は最速・最小・最も安定**. ただし Key 順を持たないため、`FindRange(PK)` と、Key 順の `All` が成り立たない. PK も世代込みのハンドルになる.

## 2. 二次索引

### 候補

| | 構造 |
|---|---|

| S2 | class ノードの B+Tree. 比較は `IComparer<TKey>` |

### 読み取れること

1. **SortedSet は不採用**. 3〜10 倍遅く、検索のたびに 440B のアロケーションが出る.
2. **アリーナ B+Tree は class 版 B+Tree より 1.3〜2 倍速い** (int / ランダムな string). int キーではメモリも同等.
3. ノードの大きさは **B = 64〜128** が最良 (範囲検索で差が出る). 64 を既定とする.
4. **string キーではアリーナ版のメモリが 2 倍** (44 vs 23 B/件). 正規化キー 8B と、配列を倍々に伸ばすことによる余りが原因. 先頭が共通の string では、速度の利点もほぼ消える.
5. **等価検索だけなら Hash が木の 3〜5 倍速い** (どのキーの型でも).
6. **値の種類が少ないキーは Bitmap** がメモリで圧勝 (3.2 B/件 = 木の約 1/6). Hash の PK 配列は走査が最速だが、1 つの値に数万件が集まると削除が遅い (4.5µs).

## 3. 結論と推奨

### 主キー側

| 要件 | 採用 |
|---|---|
| `FindRange(PK)` と Key 順の `All` が**必要** | **G: 区画分け rank テーブル** |
| **不要** | **D: 世代付きハンドル + sparse set** |

現行案 (A) と設計案の初版 (C) は、どちらの場合も採用しない. `RuntimeTable.Proposal.md` の 1 章 (64 件ブロック) は G に置き換える.

### 二次索引

| キーの性質 | 採用 |
|---|---|
| 範囲検索が必要 (既定) | **アリーナ B+Tree, B = 64**. int / short / enum は (キー, PK) を ulong 1 本に詰める |
| 等価検索のみ | **Hash** |
| 値の種類が少ない (enum, 種別など) | **Bitmap** |
| string で範囲検索が必要 | アリーナ B+Tree. ただしメモリ対策 (下記) を入れてから |

### 残っている作業

1. **Unity の IL2CPP と Mono (Boehm GC) での計測**. ここでの数値は CoreCLR と、ディストリビューションの Mono 6.8 (SGen GC) のもの.
2. G の区画配列をプールで使い回し、Mono での停止と GC 回数を減らす.
3. アリーナ B+Tree のメモリ対策: 配列を倍々ではなくチャンク単位で伸ばす (余りとコピーによる停止を無くす). string キーでは正規化キーを持たない構成も比べる.
4. 区画の大きさ (2048) の調整. 小さくするとコンパクションの停止は短くなるが、区画ごとの固定費が増える.
